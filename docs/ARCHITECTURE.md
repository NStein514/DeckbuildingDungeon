# Architecture

## Domain boundaries

`game/models`, `game/cards`, and `game/combat` implement deterministic combat without Flutter imports. JSON definitions are distinct from card instances. `resolveCard` creates an upgraded definition used by both the engine and UI, so displayed wording and applied effects agree. The engine owns mutation and exposes detached snapshots; rules never depend on animation timing.

`game/dungeon` generates a forward-only graph of thirteen rooms across six floors (ten or eleven for legacy maps). Each room connects to all nodes on the following floor. IDs, depths, encounters, and connections are stable for a seed. Two choice floors and a single boss guarantee a complete path. Version 3 maps add an event on floor three and a merchant alongside rest/treasure/shrine on floor five. Version 1/2 maps retain their original rooms and RNG sequence. Each cleared boss offers another descent. The root seed stays fixed; each descent has its own map seed and deterministic RNG continuation. Only the active map/path is stored; total cleared rooms derives from the descent count. The shared RNG state is carried into encounter seeds, rewards, and treasure selections.

`game/progression` owns run checkpoints and pure transitions. Each transition validates prerequisites, copies the checkpoint, and returns a new state. No UI mutates the published run. The state contains seed/RNG state, map, visited path, current phase, entry seed, health, gold, deck identities/upgrades, pending rewards, next instance ID, relics, and run-scoped discoveries.

`game/relics` defines four typed passive effects. Combat hooks apply starting block, extra opening draw, first-fire Burn, and increased player Poison. Enemy effects do not inherit player relics. Relic activation flows through the same effect/event processing as cards.

## Application and transactions

`RunController` uses ChangeNotifier and serializes commands by rejecting input while a save is pending. It computes the candidate state, awaits durable-store replacement, then publishes the candidate. Failure leaves both the previous in-memory checkpoint and the existing destination save in place. UI shows an error and permits retry. State snapshots returned by the controller are copies.

A battle is constructed from the saved encounter entry checkpoint. On a terminal result, the battle screen saves the run outcome automatically. It blocks result navigation until that save succeeds, with a retry action on failure. Gold and the three sampled reward IDs are written together. Choosing/skipping the reward is a separate validated transaction. Repeated commands at the wrong phase are rejected.

Returning from or reloading an unfinished battle reconstructs that battle from its entry checkpoint. This is deliberately not a mid-combat save or replay system. Completed battles cannot be replayed after their result checkpoint is saved. A process exit before a successful result save may restart the encounter, but cannot duplicate already committed rewards.

## Persistence

Run saves are envelopes with schema version 1 and content version 13. Content versions 1 through 12 remain readable: absent mapVersion defaults to 1, mapSeed to seed, and descent to 1. Old maps are validated with their original generator; their next descent uses map version 10. Missing purchases defaults to an empty list. New saves are intentionally unreadable by the older apps. Loading validates field types, resource bounds, card IDs/upgrades, unique instance identities, the generated map against its map seed and generator version, the completed path, phase-specific data, and reward structure. Unsupported or corrupt saves are preserved and surfaced; new-run replacement is disabled until a valid load. There is no automatic migration or destructive repair.

Native: `path_provider` locates app support; writes flush a same-directory `.tmp` file and rename it over the destination. Abandoned temporary writes are ignored. This targets Android/iOS file semantics; native app builds still need device verification. Browser: `package:web` performs one synchronous localStorage replacement. Quota/security errors propagate to the controller. Saves are origin-specific; one active game tab is supported. Multi-tab conflict resolution is not implemented.

Settings use a separate versioned document and a serialized write queue to prevent older slider writes overwriting newer settings. Invalid settings remain untouched and the UI explains its session-only fallback. Audio remains silent. Run discoveries and completed-room counts are local to the current journey; lifetime totals are later work. Starting-build unlocks derive from the separate journal.

## Presentation and dependencies

Flutter's built-in state tools are sufficient: local widget state handles selection, ChangeNotifier handles settings/run transactions. Riverpod and Flame add no required capability yet. Gameplay is independent of widget state, frames, and clocks. The event log retains 200 events with increasing sequence IDs, suitable for UI/debug feedback, not a full replay archive.

Art IDs map to replaceable images through an asset registry. Placeholder icons are labeled temporary. Flutter renders frames, numbers, descriptions, and effects. New cards can compose existing typed effects; new effect types require rule tests.

## Combos, fusion, and difficulty

`game/combos` contains typed, structured definitions and successful-play records. The engine resolves base card effects, relic effects, then a matching combo on a surviving target. Consecutive pairs must belong to the same turn; elemental pairs require the same target. Rejected commands do not enter history. History resets at turn start. Bonus damage is ordinary blockable damage, without attack or lightning modifiers; bonus Poison uses the existing status/relic resolver. Events drive feedback; frames do not govern rules.

`game/fusion` holds unordered two-source recipes. The run rule validates two distinct owned instances and an active shrine, removes those instances, creates a new base result, records discovery, and completes the shrine in a single copied-state transaction. Source upgrades are consumed. Failure to persist leaves sources intact. Fusion-only cards are excluded from battle rewards. The UI preserves its selections across loading/error rebuilds and supports preview, cancellation, and retry.

`game/dungeon/difficulty.dart` derives encounter definitions from the saved descent. It scales authored health by +20% and damage/block by +10% per completed descent, rounded up, preserving status amounts and original definitions. Battle construction and intent previews share these definitions, including after reload. Practice battles stay at descent 1 without room modifiers. Hardy multiplies the already-scaled HP by 1.25, rounded up; Fierce adds 2 to each scaled damage effect. The map stores each modifier and validates it against its generator version and seed. The battle UI and engine use the same modified definitions.

`game/economy` defines prices, stock generation and event costs. Merchant stock is three non-fusion, non-curse definitions shuffled from sorted IDs using the saved room entry seed. Purchases store unique tokens (`card:<id>`, `heal`, `remove`) only while the merchant is active. Every purchase validates phase, funds, availability and service conditions, copies the state, then commits wallet and benefit together. Leaving clears visit tokens and completes the room. Removal selects an exact instance and requires at least five remaining cards.

Events derive their offer from the saved room entry seed. Accept validates health/gold and writes both costs and benefits with room completion; declining completes the room without resource changes. No event rerolls on reload. Future stock/catalog or RNG changes require content-version handling.

Future survival resources should use the same controller/save boundary. `profile_repository` stores a separate profile envelope (schema version 1, content version 3; content versions 1 and 2 remain readable), using the same flushed-file or browser replacement stores. Native uses `deckbound-profile.json`; browser uses `deckbound.profile.v1`. Run content version is 10.

`PlayerProfile` is immutable. Discoveries merge by set union; records merge by maximum. Deepest floor counts entered rooms, not an unvisited next descent; bosses defeated derive from completed descents plus an active victory checkpoint. These are per-journey bests, not cumulative totals. Reconciliation is idempotent and uses bounded catalog sets and three numbers, without storing every journey.

`RunController` loads the profile separately even when the run is corrupt. For each gameplay transition it first saves/publishes the run checkpoint, then attempts to update the journal. Profile failure returns success for the already-saved gameplay action, preventing duplicate rewards or costs; a separate warning offers retry. Load/retry reconciles the profile from the current run. Run discovery and depth records are monotonic within a journey, so later checkpoints retain pending information. Before replacing a journey the controller must successfully reconcile its journal. Corrupt/future profiles remain untouched and block new-run replacement while allowing the existing run to continue. Multi-tab/multi-device merges are not supported.

Practice battles have no run-controller completion callback, so they never contribute records. Existing current runs are imported on first profile load; earlier overwritten runs cannot be recovered. No account sync or permanent combat bonuses are introduced. Content/schema changes require explicit version handling.

Map version 4 shuffles room contents among slots on each interior floor after generating the version-3 content pool. Slot IDs and edges stay stable. Entry saves a reveal phase and encounter seed before publishing any contents; continueRoom changes only the phase, without advancing RNG. Revealed paths cannot be changed. Hidden card widgets receive no room contents. Animation is presentation only and never controls rule transitions. Versions 1–3 keep their original generator and direct entry behavior.

Map version 5 preserves version-4 interior room generation and then consumes one seeded roll to choose a guardian. Versions 1–4 still generate the Warden. GuardianPlan renders the scaled enemy definition after reveal; temporary battle statuses are explicitly excluded from this preview. Existing combat intent rendering remains authoritative during a battle.

Map version 6 retains version-5 room generation and RNG consumption, but selects events from four equally sized bands of the saved encounter-seed roll. Versions 1–5 retain the original two-event mapping. Event resolution validates resources and exact card instance before applying costs and upgrades/removal to a detached copy. Deck selection shares the existing preview screen with event-specific cost wording. The controller persists the deck, resources and room completion together.

Version 7 adds floor-band and lane shuffles after legacy room generation, rebuilding slot IDs and forward edges. The original LCG methods remain for compatibility; nextFairInt samples upper 24 bits with rejection, avoiding low-bit alternation in the new map shuffles. Cosmetic tilts hash mapSeed and room ID without consuming gameplay RNG. Turn-end keeps unplayed permanent instances; new encounters still reconstruct fresh piles from RunState.deck.

Content version 8 adds Stormguard and Cinder Maul to the card catalog and fusion recipes; map generation stays at version 7. Available-recipe shortcuts select exact source instances (lowest upgrade first, then stable instance ID) without mutating the run. The existing confirmation/save boundary remains authoritative. New fusion tags keep the results out of merchant stock and regular rewards.

StartingBuild defines starter-deck substitutions and derives unlock eligibility from PlayerProfile. RunController checks eligibility inside the replacement transaction after journal reconciliation. RunRules constructs the chosen deck without consuming RNG; the saved deck is authoritative, so no build ID or save-version migration is required. Camp selection is session-local and applies only to New run; Continue and practice preserve their existing behavior.

Combat feedback is a presentation-only projection of newly emitted CombatEvents. Optional cardId, status and blocked metadata avoid parsing localized log strings. Event actorId identifies the recipient for damage/block/heal/status. CombatCue maps those events to local actor overlays, consolidates draw notices and bounds each command to 24 cues; each actor shows at most three concurrent effects. New commands replace old feedback without queuing or locking input. Actor-local RepaintBoundary/IgnorePointer/ExcludeSemantics wrappers keep effects anchored to scrolling targets and leave existing combat semantics authoritative.

Painted eight-pose sprite sequences run for 480 ms (240 ms with fast animations). Reduced-motion settings or platform disableAnimations suppress transforms/art and show a static label for 180 ms. Rules and persistence resolve immediately. A terminal battle frame remains visible only for the short feedback duration before the result view; its timer is canceled on disposal. The seven sheets are warmed on battle entry when motion is enabled, and no animation state is saved or consumed by gameplay RNG.

Map version 8 expands solo encounters to Rat/Skeleton/Mage/Duelist and ambush companions to Skeleton/Mage/Duelist, using fair sampling after legacy room construction and before floor shuffling. The opening Rat and guardian pool are unchanged. Versions 1–7 execute the original branches without the new RNG calls. A captured version-7 seed-514 fixture protects exact rooms and RNG continuation. All revealed combatants now expose the same scaled battle-plan widget; battle intent status wording identifies self versus player targets.

Merchant upgrades use the existing atomic purchase transition with an `upgrade` token and an exact-instance replacement. The service validates ownership, upgrade level, phase, funds and prior purchase. Its token persists only in the merchant phase and clears on departure; the upgraded card remains in the deck. Content version 10 recognizes the new token, while map version 8 and profile schema remain unchanged.

Map version 9 preserves version 8 layout generation and RNG consumption, expanding only the treasure relic pool to include Last Ember. Opening energy is derived from initial combat health by the synchronous engine, with no new mutable save field.

`CombatMotionPainter` plays eight distinct painted poses for each of seven visual types from 4×2 RGBA sheets. Adjacent poses cross-dissolve with premultiplied additive blending at a fixed registration and size; edge masks soften sheet boundaries. A process-wide cache decodes each sheet only once at 768 pixels wide (under 10.5 MiB total decoded RGBA). Missing artwork leaves text feedback available. Duplicate visuals are coalesced per actor; generic support artwork is suppressed when another effect is present, while all labels remain. Normal/fast/reduced timing is 480/240/180 ms. Reduced motion omits the painter entirely.

Map version 10 rerolls only existing nonstandard combat slots after version-9 layout generation, using fair seeded selection among Hardy, Fierce, Rallying and Mending. Room types, identities, edges, enemy compositions, opening combat and guardians are preserved for a given map seed. The extra rolls advance the new map RNG; versions 1–9 execute unchanged. A version-9 seed-514 fixture protects exact layout and RNG continuation.

`scaleEnemy` appends Rallying's self-targeted Strength effect or Mending's self-targeted heal once per authored action, after scaling its base effects. These fixed bonuses use existing combat/status/heal handling and feedback animations. Live healing intents explicitly name their recipient. No new artwork or animation assets are introduced in this milestone. Save content version 12 supports the new map and modifier IDs; profile content remains version 2.

Content version 13 and profile content version 3 add Venom Ward and Bloomguard. Both use existing typed block/status/heal/exhaust effects, shared upgrade rules and the atomic fusion transaction. No new mutable combat state or map generation changes are required. Seven recipes drive shrine shortcuts, discovery counts and starter unlocks. Fusion tags exclude these cards from seeded merchant/reward pools, preserving previous pool order and RNG consumption.
